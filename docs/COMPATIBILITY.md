# AzerothSurvivorsSpeedGear 兼容说明

## 当前设计与证据边界

本项目面向原生 Windows x64 Azeroth Survivors。Lua AddOn 提供游戏内控制，原生后端负责真实变速。安装器核对 PE 架构和 `dwmapi.dll` 导入，不更改游戏 EXE；这一检查只证明当前引导方式具备加载条件，不能证明全部模拟逻辑兼容。

当前 `SG1` 协议使用自定义 CVar。0.3.0 首选 `ConsoleExec` 查询 CVar 的同步日志，经本地 stdout/stderr 管道即时传递；配置文件 `benilla-config/config.toml` 作为后备。原生组件只提取严格匹配的本插件控制信息，不记录控制台内容，其他输出原样转发。两个通道共用会话及序列检查，拒绝迟到文件覆盖新指令；每秒查询心跳与每五秒落盘刷新分别处理。后端默认 1×，失联 8 个真实秒恢复 1×。

0.4.0 使用独立有界日志转发，输出堵塞不再与命令读取共用工作线程；过载允许丢弃旧转发日志字节，不丢弃已解析的控制指令。有效 console 回执在 2.5 秒内视为健康，后备配置每秒扫描一次；超过此窗口恢复 100ms 扫描，8 秒失联保护仍每 100ms 检查。健康状态来自通过会话、序列及新鲜度校验的消息，不能由句柄安装成功或旧文件副本刷新。

即时通道中断后，当前指令的第一次完全相同且仍新鲜的文件回显允许接管一次心跳期限，避免 0.25× 时约四秒保存等待造成 8 秒期限先于下一条文件指令到达。该接管每个序号最多一次，后续文件副本不续命，旧会话、低序号、不同内容或过期回显仍拒绝。

`AZSSpeedGear-status.json` 每秒原子刷新，记录真实后端状态；`scripts/Status.ps1` 只读显示并拒绝未知格式/过期或未来报告。Lua 沙箱没有可用的实时回执读取接口，面板只陈述发送方式及游戏计时实测值。它不通过私有 VM 地址、输入注入或修改游戏语言文件来伪造确认。

即时通道依赖游戏查询日志的格式、INFO 输出以及 Windows 标准句柄。自定义日志过滤可能使其退回较慢的配置通道；未来游戏更新改变日志、CVar 持久化、保存时机或插件运行周期时，必须重新验证。没有调用游戏 VM 的私有 ABI，也不硬编码标准输出函数地址。

0.3.0 保留 `timeGetTime` 自身的原始毫秒时钟，正确展开其 32 位回绕后连续缩放，避免用较粗的 `GetTickCount64` 替代造成高倍速下的阶梯跳变。倍速显示使用完整观测窗及 10% 进入、20% 退出阈值；它是游戏计时的近似测量，不能证明所有模拟与画面都稳定。

0.2.0 增加独立可拖动浮窗和 14 语言目录。原生组件读取 `%APPDATA%/wenilla-rogue/language.txt` 的白名单代码，原子生成本插件的 `NativeLocale.lua`，下一次进入世界时由 Lua 载入。经典 `GetLocale()` 不能完整表达所有自定义游戏语言，仅在缺少原生提示时作为回退；可用时也会参考已载入 HUD 的语言。若游戏改变语言文件位置/代码格式，需要重新适配。浮窗及面板位置与语言选择分别处理，语言刷新不会重置位置或倍率。

原生文件名为 `dwmapi.dll`，与已安装 SurvivorsDragonUi 的 `avrt.dll` 分开。安装器拒绝覆盖无法通过 AZSSpeedGear 安装收据及 SHA-256 验证的同名 DLL；不尝试 DLL 链式加载，不修改 DragonUI 文件。

## 自动识别的含义

0.5.0 增加独立启动更新入口、正式包校验和每六小时的官方更新监测。官方 EXE 在 GitHub Windows runner 中只读检查，记录精确哈希、来源提交、扫描器指纹和 CI 运行号；文件不会发布到本仓库或插件发行包。指纹相同时可复用相同扫描器的已有检查结果，扫描器或导出列表改变后需重新检查。

启动入口会比较安装收据中的游戏指纹与当前 EXE，并查询匹配的远端报告。原生加载仍执行独立扫描，远端 `structural_only` 不能跳过本次校验；`unknown` 和 `unsupported` 不能升级成实机验证。新的适配逻辑必须作为经过 CI 的插件正式版本发布，自动更新器只接受固定仓库的正式版本、匹配资产名称/大小/GitHub SHA-256 与完整文件清单，不执行兼容报告中的内容。

如果游戏不再导入 `dwmapi.dll`，原生组件连启动机会也没有。因此更新检查保留在独立启动入口中；只从游戏 EXE 启动不会执行这个入口的下载检查。此边界以及未知加载/API变化都不能用“未来永不失效”描述。

目标是扫描识别当前 EXE 的 **25 ms 本地模拟等待**，并验证唯一性、调用关系和相关指令；不依靠单一游戏 EXE 哈希白名单作为唯一匹配条件。扫描与验证通过后才允许启用相应变速路径。

这只能扩大自动识别的可能范围，不能预先保证任何未来版本。以下变化可能需要维护新适配：

- 编译器、指令序列、模拟线程调度或等待机制改变。
- 原来独立的模拟等待被内联、合并或移除。
- 存在多个含相同常量的等待位置，无法确认正确调用者。
- 原生 DLL 加载策略、DWM 导入或可执行文件架构改变。
- CVar、配置格式或游戏内插件 API 改变。

未知结构应拒绝高倍率并保持 1×；扫描产生候选本身不是成功适配的证据。只缩放时钟可能造成画面、计时与模拟速度分离，应分别测量。

## 测试记录要求

每次实机记录应包含：游戏显示版本、完整 EXE SHA-256、AZSSpeedGear 版本、原生扫描状态、实际倍率测量、插件组合、失联恢复和正常退出结果。计时测量以未被后端变速的外部墙钟为基准，并将暂停、选卡和读图时间分开。

安全回退、编译通过、离线测试和实机对局是不同证据。安装器的校验通过不能替代游戏行为验证。
